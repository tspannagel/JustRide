KICKR Head Unit

An ESP32-S3 box on the handlebar that controls a Wahoo KICKR Core over Bluetooth, reads every Zwift controller, runs structured workouts from a microSD card, and shows power, cadence, speed and heart rate on a 4″ square touchscreen. No cloud, no 3D world, no subscription.

Waveshare ESP32-S3-Touch-LCD-4BLE FTMSZwift ZAP protocolESP-IDF + NimBLE + LVGL.zwo in · .fit + .csv outDuckDB-WASM stats

01Goals & scope

Must have (v1)

  • Connect to KICKR Core via FTMS; read power, cadence, speed.
  • ERG workouts from .zwo files on microSD, scaled to the rider's FTP.
  • Free ride in SIM mode with a flat or set grade.
  • All Zwift controllers as input: Click v1, Click v2, Play, Ride.
  • Virtual shifting (24-gear table) driven by the controllers.
  • Record every ride to a .fit file locally.
  • 4″ 480×480 touchscreen dashboard; navigable entirely from the controllers.

Nice to have (v2+)

  • BLE heart-rate strap; external power meter for power match.
  • Wi-Fi file manager: upload workouts, download rides, OTA updates.
  • Statistics app in the browser (DuckDB-WASM), served by the unit itself.
  • Auto upload to intervals.icu (API key, no OAuth).
  • Elite Sterzo, generic BLE HID remotes.
  • Fan speed by power or heart rate through a smart plug (the board has no free GPIO for a fan header).
  • Re-broadcast as an FTMS peripheral so a watch can record too.

Out of scope

  • 3D world, multiplayer, ANT+ (needs extra radio and licensing).

03Hardware

One ready-made board, no soldering. Everything the plan needs is on it except the power supply and a case.

Waveshare ESP32-S3-Touch-LCD-4 (V3)

  • ESP32-S3-N16R8: 16 MB flash, 8 MB octal PSRAM, BLE 5, Wi-Fi
  • 4″ IPS, 480×480 square, ST7701 on a 16-bit RGB bus
  • GT911 capacitive touch, 5 points
  • microSD slot (SPI)
  • Onboard buzzer
  • PCF85063 RTC with rechargeable backup cell connector
  • SW6106 battery chip, PH2.0 connector for a 3.7 V LiPo
  • USB-C for power, flashing and logs
  • RS485, CAN and 7–36 V terminal: present, unused here

What this means for the design

  • No free GPIOs: the panel, SD card and buses use them all. Extras like a fan run through Wi-Fi or Bluetooth instead of wires.
  • Backlight, LCD reset, touch reset, SD chip select and buzzer sit behind a TCA9554 I/O expander on I2C.
  • The display needs full frame buffers in PSRAM, which affects how LVGL and Wi-Fi are configured (see board bring-up).
  • Navigation is touch plus the Zwift controllers; there are no hardware nav buttons.

Power rules (any board)

Use a plain 5 V USB supply with a USB-A to USB-C cable. Don't use laptop or phone fast chargers. Waveshare's wiki for this board reports fast-charge sources (up to 20 V) burning out protection parts. In theory a board that never negotiates higher voltage only gets 5 V, but a €5 plain supply removes the risk entirely.
The SW6106 battery chip can switch the board off at light load. The wiki describes a fix by writing I2C registers. The firmware applies it at boot, and the board-support module re-applies it if the chip reports a reset.

Board bring-up order

The shared pins make the order at boot matter. The board-support module does this once, before any other task starts.

1. I2C on SDA 15 / SCL 7  →  probe TCA9554, GT911, PCF85063, SW6106
2. SW6106: write the light-load register fix so the board stays on
3. TCA9554: backlight off, pulse LCD reset (EXIO2) and touch reset (EXIO0)
4. ST7701 init over 3-wire SPI on GPIO 1 / 2 / 42, then CS 42 high for good
5. Start the RGB panel (esp_lcd_panel_rgb), two 480×480 RGB565 frame buffers in PSRAM
6. Re-configure GPIO 1 / 2 / 4 as the SD SPI bus, CS via EXIO3, mount FATFS
7. Backlight on (EXIO1), start LVGL, then BLE, then the control loop
// RGB + PSRAM tips: PSRAM at 80 MHz octal, bounce buffers on,
// CONFIG_SPIRAM_FETCH_INSTRUCTIONS / RODATA on, keep Wi-Fi off while riding

Zwift controllers · Zwift Accessory Protocol (ZAP)

All four Zwift controllers share one custom GATT service with three characteristics. After a handshake the controller streams protobuf messages with the button state. The UUIDs and handshake below come from community reverse-engineering; confirm them with nRF Connect on your own devices before writing the driver.

CharacteristicUUID (per community docs, verify)PropsUse
Zwift service00000001-19CA-4651-86E5-FA29DCDD09D1—Scan filter (also check manufacturer data for device type and left/right)
Async00000002-19CA-4651-86E5-FA29DCDD09D1notifyContinuous button / analog state
SyncRX00000003-19CA-4651-86E5-FA29DCDD09D1writeHost → controller: handshake, keep-alive, haptics
SyncTX00000004-19CA-4651-86E5-FA29DCDD09D1indicateController → host: handshake reply, battery

Encrypted variant (Play, Click v1)

  1. Host writes "RideOn" + its 64-byte P-256 public key.
  2. Controller replies "RideOn" + its public key.
  3. ECDH shared secret → HKDF-SHA256 → AES-CCM session key.
  4. Each Async packet: counter + ciphertext + short tag. Decrypt, then parse protobuf.

mbedTLS in ESP-IDF provides all three primitives with hardware acceleration.

Plain variant (Ride, Click v2, newer firmware)

  1. Host writes "RideOn" without a key (or with an "unencrypted" flag).
  2. Controller replies "RideOn".
  3. Async packets are plain protobuf, e.g. message ID 0x23 on the Ride carries a button bitmap plus analog paddle values.

The driver tries plain first and falls back to encrypted on rejection or garbage data.

09Virtual shifting

The KICKR Core has no built-in virtual shifting unless it is the Zwift edition, so the head unit does it. The rider leaves the real chain in one gear (middle of the cassette) and the shift buttons move through a virtual gear table.

Strategy A · grade scaling in SIM (v1)

Send FTMS Simulation with an adjusted grade so a harder virtual gear feels like a steeper road at the same cadence.

k = virt_ratio / real_ratio
grade_cmd ≈ (grade + Crr) × k − Crr
// small-angle, ignores aero; tune by feel
// clamp to −10 … +20 %, max 2 writes/s

Simple, uses the trainer's own flywheel feel, works on any FTMS trainer. Less exact at the extremes.

Strategy B · physics to ERG (v2)

Compute virtual speed from cadence × virtual gear × wheel size, then the power that speed needs on the road, and send it as an ERG target at 2–4 Hz.

v = rpm/60 × ratio × 2.105 m
P = v·(m·g·(sinθ + Crr·cosθ)) + ½ρ·CdA·v³
// smooth P, send Set Target Power

Exact and trainer-independent, but ERG lag makes sprints feel delayed.

11Statistics with DuckDB-WASM

DuckDB can't run on the ESP32, but it runs inside any modern browser. The unit serves a small statistics app from its SD card; your phone or laptop downloads it once and runs every query locally. No cloud, no install.

Where the analysis happenseverything stays on your devices

What the device writes

The Recorder writes a CSV next to every FIT file and appends two small rows at ride end. Computing the summary and best efforts on the device is cheap (a sliding window over the ride already in PSRAM) and means the all-time views never need to load every second of every ride.

FileColumns
rides/<id>.csvt_s, ts_utc, power_w, cadence_rpm, speed_kmh, hr_bpm, target_w, grade_pct, gear, interval_idx, mode, lap
rides/summary.csvride_id, start_utc, duration_s, moving_s, workout, ftp_w, avg_w, np_w, if, tss, kj, avg_hr, max_hr, avg_cad, distance_km, fw
rides/bests.csvride_id, duration_s, watts · durations 1, 5, 10, 30, 60, 120, 300, 600, 1200, 1800, 3600 s

How the stats app loads

  1. Browser opens http://trainer.local/stats/ (mDNS). App shell is about 100 KB.
  2. DuckDB-WASM (one EH bundle plus its worker, a few MB pre-gzipped) loads from the unit once, then comes from the browser cache.
  3. The app opens a persistent database in the browser's private file storage (OPFS) and checks which rides it already has.
  4. GET /api/rides returns the ride list; only new CSVs are fetched and inserted.
  5. All queries and charts run locally. If OPFS is not available, the app uses an in-memory database and re-imports.
Keep the stats app on the SD card under /www/stats, not in the 16 MB flash. It can then be updated by copying files, separately from the firmware.

Views

Overview

  • Fitness, fatigue and form (CTL 42-day, ATL 7-day, TSB) from daily TSS
  • Weekly hours, TSS and kJ

Example queries

-- Import a new ride fetched from the unit
INSERT INTO rides SELECT '2026-10-26_0715' AS ride_id, * FROM read_csv('2026-10-26_0715.csv');

-- Weekly load
SELECT date_trunc('week', start_utc) AS week, sum(tss) AS tss, round(sum(duration_s) / 3600, 1) AS hours
FROM summary GROUP BY week ORDER BY week;

-- Power curve: all-time vs last 90 days
SELECT duration_s,
       max(watts) AS best_all,
       max(watts) FILTER (WHERE start_utc > now() - INTERVAL 90 DAY) AS best_90d
FROM bests JOIN summary USING (ride_id)
GROUP BY duration_s ORDER BY duration_s;

-- Time in Coggan power zones for one ride
SELECT CASE WHEN power_w < 0.56 * ftp_w THEN 'Z1' WHEN power_w < 0.76 * ftp_w THEN 'Z2'
            WHEN power_w < 0.91 * ftp_w THEN 'Z3' WHEN power_w < 1.06 * ftp_w THEN 'Z4'
            WHEN power_w < 1.21 * ftp_w THEN 'Z5' ELSE 'Z6+' END AS zone,
       round(count(*) / 60.0, 1) AS minutes
FROM rides JOIN summary USING (ride_id)
WHERE ride_id = '2026-10-26_0715' GROUP BY zone ORDER BY zone;

-- Interval compliance
SELECT interval_idx, avg(target_w) AS target, avg(power_w) AS actual,
       round(100 * avg(power_w) / nullif(avg(target_w), 0)) AS pct
FROM rides WHERE ride_id = '2026-10-26_0715' AND target_w > 0
GROUP BY interval_idx ORDER BY interval_idx;

CTL and ATL are exponential averages over daily TSS. DuckDB has no built-in exponential moving average, so the app takes daily TSS from SQL and computes them in a few lines of JavaScript.

14Risks & open questions

RiskImpactMitigation
Zwift changes the controller protocol in a firmware updatehighDriver per protocol version, raw-dump debug mode, hold off on controller firmware updates, physical buttons as fallback
Encryption details differ from community docsmediumDo M4 (plain) first; capture real traffic with an nRF52840 sniffer before M5
BLE airtime with 5–6 links causes dropoutsmediumControllers at 15–30 ms interval, trainer and HR at 50–100 ms; turn off Wi-Fi while riding; NimBLE max connections = 6
KICKR allows only 3 BLE connections; Zwift app on another device may hold onelowShow "trainer busy" message; only one app should send control at a time
SD card corruption on power lossmediumJournal + periodic fsync; finalize FIT on next boot
Fast-charge USB supply damages the boardhighPlain 5 V USB-A supply and USB-A to C cable only
SW6106 switches the board off at light loadmediumRegister fix at boot (Waveshare FAQ), re-applied on chip reset
Pin table in the wiki contradicts itself (I2C pins)mediumCheck V3 schematic PDF; I2C scan at first boot
Screen flicker or shift while Wi-Fi is busy (RGB panel + PSRAM)mediumBounce buffers, 80 MHz PSRAM, Wi-Fi only off the bike
DuckDB-WASM first load is slow over ESP32 Wi-Fi and SD over SPI (several MB)lowServe pre-gzipped with long cache headers and ETag; one-time wait of a few seconds, then cached by the browser
Older browsers or private mode without OPFSlowFall back to an in-memory database and re-import rides each visit
Display readability, glare, sweatlowIPS panel, high-contrast dark theme, conformal coating, enclosure with drip edge
Legal: reverse-engineering for interoperabilitylowPersonal, non-commercial use; don't redistribute Zwift binaries or keys

Open questions

  • Which controllers do you own today? That decides whether M4 or M5 comes first.
  • Firmware framework: ESP-IDF (recommended for NimBLE multi-link control and LVGL performance) or Arduino-ESP32 for faster prototyping?
  • Do you want the unit to record alone, or also re-broadcast so a Garmin/Wahoo watch records the same ride?
