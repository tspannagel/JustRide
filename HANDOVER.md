# Handover: KICKR Head Unit

Planning was done in a Claude chat on 26 Oct 2026. Firmware for M0–M3b and M6 (strategy A) was written the same day, **without a compiler or hardware**. Read `CLAUDE.md` first; `docs/plan.html` has the full plan with diagrams.

## Status

- Planning: done (hardware choice, protocols, architecture, data formats, stats app, milestones).
- Hardware: the user's board is a **V4.0** (REV 4), not V3 (2026-10-28). `bsp.c` was ported to V4 from Waveshare's V4 BSP: CH32V003 helper at 0x24 instead of TCA9554 + SW6106, SD over 1-bit SDMMC, Waveshare's ST7701 init table and 16 MHz timing. First boot on the board: CH32, RTC (0x51) and GT911 (0x14) respond, the device reaches `jr>`, BLE scans. LVGL's built-in 64 KB pool overflowed while building the screens (hang); now `CONFIG_LV_USE_CLIB_MALLOC`. Later the same day: picture correct after switching to one frame buffer + LVGL partial rendering (direct mode on two buffers ghosted); touch works after driving GT911 INT (CH32 EXIO2) low through reset; SD mounts after enabling internal pull-ups (~1.5 MB/s write, ~1 MB/s read). After `idf.py flash` with a card inserted the USB console sometimes stays silent until the board is re-plugged. Open: backlight PWM polarity, the 0x5e seen in post-boot scans (likely a scan/touch-poll clash).
- Firmware: everything is written, including Zwift Ride support (unverified button table) and multiple riders (2026-10-27). **The firmware compiles and links with ESP-IDF 5.3.2 in CI and on the user's Mac** (`.github/workflows/ci.yml`; 1.6 MB image, 73 % of the app partition free). Display, touch, SD, the Zwift Ride and the KICKR connection run on the user's V4 board (see Hardware); ride behaviour on the trainer is still to be checked. `dependencies.lock` is committed (pins component versions).
- Verified off-device: pure components (proto_ftms incl. the control-point state machine, workout/zwo, metrics, vshift, ride, recorder CSV/FIT) pass host tests under ASan/UBSan; FIT output decodes with fitdecode; the statistics app runs in headless Chrome against CSVs from the real recorder code.
- MCP server (2026-10-31): `tools/mcp_server.py` lets Claude read stats and add workouts over the device's web API (manual 7.9). Tested against `web_dev.py` samples (mcp 1.30 and 2.3, stdio); not yet tried against the real head unit or in Claude Desktop.
- User manual: `docs/manual.html` with screenshots rendered from `main/ui.c` by `tools/ui_shots/shots.sh` (device screens) and of the stats app with generated sample rides.

## Decisions made

| Topic | Decision |
|---|---|
| Framework | ESP-IDF ≥ 5.3, C11 (confirmed 2026-10-26) |
| Riders | Up to 8 in settings.json, picked on the home screen; per rider: rides folder, FTP, max ERG, weight (W/kg only), max HR (HR zones), HR strap. FTP is only suggested after a ride (95 % of best 20 min), never applied automatically (2026-10-27). Built-in FTP ramp test (2026-10-30): weight-based steps, auto-end into cool-down, 75 % of best minute, applied at once with a "Keep old FTP" undo on the summary (first test ride: the offer was missed), `ftp_known` flag drives the prompts; fail thresholds (60 rpm / 80 % / 10 s) still to be tried on the KICKR |
| Controllers owned | Zwift Ride only → plain ZAP implemented (M4); encrypted ZAP (M5) not needed for now |
| FIT | Own ~300-line encoder instead of the Garmin SDK (validated with fitdecode) |
| Stats persistence | No OPFS (needs a secure context; plain-HTTP LAN isn't). Small CSVs per visit, ride CSV on demand |
| Stats vendor files | Generated by `tools/vendor_stats.sh` (pinned), not committed (34 MB wasm) |
| Wi-Fi credentials | In `/config/settings.json` on the SD card, not NVS (editable on a computer, no flash wear) |
| OTA authorization | Physical presence: tap "Allow firmware update" on the device, valid 5 min |
| Crash journal | The per-second CSV itself (fsync every 10 s) + `/rides/.journal` with ride metadata |
| Board | Waveshare ESP32-S3-Touch-LCD-4 **V4.0** (user's board, 2026-10-28), no soldering, no custom PCB |
| Power | Plain 5 V USB-A supply + USB-A to C cable; no fast chargers |
| Trainer protocol | Bluetooth FTMS (not Cycling Power, not ANT+) |
| Controllers | All Zwift controllers: Ride, Click v2 (plain ZAP), Play, Click v1 (encrypted ZAP); Sterzo and BLE HID later |
| Navigation | Touch + Zwift controllers; no hardware buttons |
| Workouts | `.zwo` files on microSD, ERG with FTP scaling |
| Virtual shifting | Strategy A (SIM grade scaling) first, strategy B (physics → ERG) later |
| Recording | FIT + per-second CSV + summary/bests CSV, all local |
| Web app | Served by the device from SD (no internet): statistics, workout builder + generator, training plans; DuckDB-WASM only for the SQL console |
| Wi-Fi | On at start-up and after each ride (files, stats, OTA); off while riding |
| Out of scope | 3D world, multiplayer, ANT+ |
| Case | User designs their own from Waveshare's official STEP model (wiki → Resources → "3D STP") |

## Adaptive workouts (built 2026-10-29, not yet ridden)

User's choices: HR range adjusts power; an average watt goal is held (shortfalls made up later); cadence is a cue only; set up from builder blocks, generator presets (HR zone 2, Steady average) and a device quick start (Workouts → Zone ride).
- `.zwo`: `SteadyState` with `JrHrLow/JrHrHigh`, `JrAvg="1"`, `JrCadLow/JrCadHigh`, `JrMin/JrMax` (FTP fractions). Parsed into `goal_t` (≤ 16 per workout, `segment_t.goal` 1-based). Zwift ignores the attributes.
- Controller in `ride.c` (`adapt_update`, once per recorded second, host-tested): HR above range −5 W / 20 s (−10 W if > 5 bpm above), below +5 W / 20 s (not in hold-average parts); no HR → never raises, after 60 s back towards plan; hold-average spreads the shortfall over the remaining part (≥ 60 s), capped by the HR ceiling. Always within the part's bounds (default −30 % / +15 %, ≥ 30 % FTP) and Max ERG; sent in 5 W steps. Cadence: beep after 5 s out of range, ≤ 1 per minute.
- HR zones (2026-10-31, user: % of max HR, max HR offered after rides): 5 zones as the stats page (`metrics_hr_zone`, < 60/70/80/90 %); to ride in one, Z1 = 50–60 % … Z5 = 90–100 % (`metrics_hr_zone_pct`). `JrHrLow/JrHrHigh` both ≤ 1 are fractions of max HR (`goal_t.hr_pct`); `ride.c` turns them into bpm with `ride_config_t.max_hr` (`goal_hr`), so files, plans and the quick start follow the rider's current max HR. Ride screen shows the HR zone; summary offers "Set max HR" when the ride's best 10 s HR (`max_hr_peak`, every second with HR) beats it, never applied silently. Old bpm files still work. Not done: HR-reserve/LTHR zones.
- To verify on the bike: HR step sizes feel right (KICKR response lag), the cadence beep isn't annoying, hold-average after a pause.
- Not done: interval-failure rules (lower the next repeat), learning from adjustments in the web app.
